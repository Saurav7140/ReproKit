# Architecture and feasibility

Current delivery: Phases 0–8 complete. [Phase 8 verification](verification-phase8.md) records current workflows, limits, clean source-copy checks and release boundaries. The Phase 0 proposals below are historical; implemented capture/replay/hosted designs supersede them.

## Implemented Phase 7 website boundary

`@reprokit/recorder` exposes explicit website start/stop/discard and snapshot subscriptions. Construction is inert. The host owns consent and the trigger; `apps/sdk-demo` is a separate integration on 5176 and supplies accessible consent, controls, shared review/export and deliberate submission. SDK and extension use the same rrweb recorder, masked error/Resource Timing diagnostics, bounded CaptureBuffer and v4 schema. A page marker rejects overlapping recordings. Reload/navigation loses same-page report memory; nothing resumes. The extension adds no permissions.

The separate `reprokit-public` Edge Function accepts only bounded current website SDK JSON through `POST ?key=UUID`, without user tokens. Owner-enabled `website_intakes` map public keys and one exact origin to a private project; owner RLS/configuration RPCs gate enable/rotate/disable. Service-only RPCs charge 10 attempts/hour against a stable intake identity, recheck enabled key/origin at reservation, and cap the project at 20 retained reports. They use the existing owner lock, immutable payload hashes, 15-minute leases, server-generated paths, private Storage and write-before-ready completion. Cleanup also expires old public counters. Rotation preserves quota; already reserved uploads may finish after disable. No public read/list/status/delete or private URL/metadata is exposed. The authenticated extension/dashboard API remains separate and verifies bearer identity and ownership.

Origin/CORS is a browser constraint, not authentication; keys and headers can be copied/forged. Quotas bound accepted data, not repeated invocation costs or malicious report truth. Attackers can exhaust quota. The backend needs upstream bot/invocation protection before broad exposure. [Full threat model, API/run guide and limits](website-sdk.md), [local/live verification](verification-phase7.md). Frontends/packages remain unpublished; the authorized additive migration and public function are installed in the configured project.

## Phase 6 extension connection

`apps/extension/src/Connection.tsx` owns a separate Supabase client per trusted review page. Existing-account email/password sign-in, project refresh/selection, explicit upload and disconnect are local UI actions. `persistSession: false` and disabled URL session detection keep tokens out of persistent storage and prevent URL-token injection. No dashboard/website token bridge, worker, storage/identity permission or host permission was added. Closing/reloading discards both report and connection; sign-in is intentionally per review page.

`apps/shared/hosted-request.ts` shares bounded calls and one refresh-on-401 retry with the dashboard. A specific auth error clears expired extension state without changing the report. Network/timeouts/provider errors preserve evidence. Disconnect clears the client immediately and attempts server sign-out separately, including offline. Details must be saved first; duplicate clicks are guarded and stale completions cannot attach an old link to a replacement report. Existing backend hashes/idempotency remain authoritative.

Builds reuse dashboard public URL/key settings unless explicitly overridden. The generated manifest allows only that Supabase origin through `connect-src`, or no connections when unconfigured. Capture/replay sub-builds do not recopy the source manifest over the generated policy. All SDK code is local; content/MAIN capture bundles and web-accessible resources contain no auth client/token. Replay's own CSP still blocks networking. [Chrome network model](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests).

The function accepts valid `chrome-extension://` origins for CORS alongside the dashboard, accommodating different unpacked/store IDs. Origin is not authentication: user bearer validation, ownership, RLS, limits and cleanup are unchanged. Tests verify extension Origin/public key cannot replace a session and arbitrary web/opaque origins fail. Function version 2 was deployed; no schema/auth-provider change was required.

Saved links contain validated project/server-report UUIDs, never credentials. After sign-in, the dashboard confirms the project belongs to the current owner, fetches scoped metadata and opens the existing viewer. Invalid/unavailable links show fixed errors without minting a read URL. Isolated browser fixtures verify configured/unconfigured modes; a separate live run proves actual capture → review → extension sign-in/upload → exact dashboard report/replay, duplicate retry and offline preservation. [Phase 6 evidence](verification-phase6.md).

Research date: 2026-11-03. The Phase 0 decisions below preceded UI work. Implemented Phase 2/3 designs and deviations are documented at the end. “Documented” means supported by upstream documentation; “verified” requires the named local check.

## Workspace and boundaries

`packages/core` owns v1–v4 reports, bounded validation, privacy allowlists, portable files and reproduction drafts. `packages/recorder` shares rrweb, diagnostics, locators and the bounded buffer between extension capture and the optional website SDK. `apps/dashboard`/`apps/extension` share investigation/replay controls through `apps/shared`; `apps/demo` provides deterministic failures and `apps/sdk-demo` integrates the SDK separately. Supabase holds both migrations, distinct authenticated/public functions, private storage and leased retention. Root tooling supplies TypeScript, tsx tests, PGlite/PostgreSQL, Playwright and standalone native-browser verification. Production builds emit separate attribution files; the server validator builds before server tests.

Intended Phase 2 flow: explicit start in extension -> selected-tab isolated content script + minimal MAIN-world diagnostics -> validated/sanitized messages -> bounded tab-local buffer -> explicit stop -> full extension review page. The service worker coordinates permissions and lifecycle, not the sole recording buffer. No automatic upload.

## Support policy

Verified Phase 8 target: desktop Chrome 156.0.8078.80 and Edge 156.0.4314.58 on Windows x64, plus bundled Chromium 156.0.8078.4 for the product regression suite. MV3 capture is top-level HTTP(S) HTML only. The manifest's minimum 120 is a technical floor, not an every-version test claim. Exclude browser-internal pages, stores, other extensions, PDFs, file URLs, incognito, cross-origin frames, closed shadow roots, canvas/WebGL/video contents and native applications. Firefox/Safari and other OS/hardware combinations are unverified/unsupported. [Known limits](known-limitations.md).

## Technical findings and decisions

| Area | Documented behavior / decision | Verification still required in Phase 2 |
| --- | --- | --- |
| MV3 lifecycle | Workers can suspend and lose globals. Keep capture ownership in the tab; a popup cannot own capture. | Worker suspension, recovery, and review handoff. |
| Permissions | Start with activeTab + scripting when capture exists. activeTab grants temporary access on a user gesture, survives same-origin navigation, and ends on cross-origin navigation. Phase 1 requests **zero** permissions. | Restricted pages, permission denial and revocation. |
| Worlds | ISOLATED code sees DOM but not page JS wrappers. MAIN-world instrumentation is needed for page fetch/XHR observation. Page scripts can interfere with it. | Bundle injection under page CSP; errors/rejections; safe restoration. |
| Messaging | Treat every page message as hostile, even with a per-session nonce. Check source window, frame/tab/document identity, origin, active-session identity, type, size, rate, and field allowlist. A nonce is routing, not authentication. Never accept upload/privileged commands from page messages. | Forgery, stale frames, oversized messages, flood tests. |
| Early errors | Late injection cannot recover prior errors or previously retained fetch references. | Explicit optional “restart recording after reload” requires a separate consented, scoped document_start registration; not promised for initial capture. |
| Network | Observe page fetch rejection and HTTP >=400 separately; fetch resolves on HTTP errors. Observe XHR loadend plus error/abort/timeout, status 0 is ambiguous. Never read bodies or headers. | Preserve this, arguments, original return/rejection, abort semantics and XHR events; restore only if wrapper is still ours. Workers and pre-injection calls remain gaps. |

Reload/full navigation ends the document recording; **do not silently resume**. Tab closure or browser restart ends capture and loses unsaved tab memory. Same-document navigation may continue, with sanitized URL events. A surviving full review page may hold a stopped report only for its lifetime. No across-reload capture claim is made. Phase 2 must expose interrupted/end reasons and gaps.

Sources: [Chrome lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle), [activeTab](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab), [content script worlds](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts), [scripting API](https://developer.chrome.com/docs/extensions/reference/api/scripting), [fetch semantics](https://developer.mozilla.org/en-US/docs/Web/API/Window/fetch), [XHR loadend](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequestEventTarget/loadend_event). These are API feasibility findings, not observed recorder behavior.

## rrweb suitability

Use upstream rrweb, never a custom replay engine. Current upstream recommends split `@rrweb/record` and `@rrweb/replay` packages; the old `rrweb` package is deprecated. Candidate recorder version: 2.2.0. Locally bundled code is required for MV3. The dev-only synthetic spike evaluates record options without enabling capture in any app.

Required privacy configuration: maskAllInputs, global text masking, blockSelector for `[data-reprokit-mask], .rr-block` and contenteditable, disable canvas/cross-origin iframe capture, inline images, stylesheet inlining, and fonts. Disable console and network-body plugins. Configuration is insufficient for attributes, CSS URLs, meta URLs, and identifiers; a field-aware sanitizer must run synchronously before the recording buffer and before crossing the page bridge. Unsupported event shapes must be dropped, not forwarded unchanged.

Replay must run on a dedicated viewer surface with a restrictive CSP and a sandboxed rrweb iframe without allow-scripts; never enable UNSAFE_replayCanvas. Strip active content, URLs/CSS resource references, event attributes and embedded objects before replay. Block external asset/network loads by default, including CSS imports, images, fonts and frames. No remote asset proxy or automatic fetch. Visual fidelity is intentionally reduced. CSP + sanitizer + adversarial browser tests are a Phase 3 gate; a schema check alone does not make replay safe.

Source: [rrweb guide and option tables](https://github.com/rrweb-io/rrweb/blob/main/guide.md). Exact installed API and spike results are recorded in [verification](verification.md). The spike confirmed form/text/region masking for initial snapshots and tested mutations, the stop callback, and the expected unmasked attribute/URL gap. End-to-end recorder integration remains unverified until Phase 2; loading the Phase 1 MV3 shell is verified separately.

## Report v1

Common: formatVersion=1, UUID id, source (platform/method), title/description, ISO startedAt/endedAt, bounded sanitized environment, timeline, suggestedSteps, limitations, and explicit capability states. Evidence is a discriminated union: `web` (sanitized page, actions, errors, failed requests) or `none` (non-web/manual evidence unavailable). A small explicit union avoids assuming every report has browser evidence.

Capability values are `available`, `unavailable`, or `unsupported`; the six named channels are interactions, replay, errors, requests, environment, playwright. v1 foundation cannot accept replay or generated test payloads, so those channels cannot be declared available. A later schema version must define and validate rrweb events and source exports before ingestion. Unknown keys and unknown versions are rejected rather than passed through. The fixture exercises metadata only; no imported content is replayed or executed.

Limits: 5 minutes, 10,000 timeline events, 5 MiB UTF-8 JSON. Per-field and evidence-array limits apply as well; events must be chronological and inside capture bounds. Validation rejects unsupported versions before parsing evidence. Parsing is validation, **not sanitization** and cannot certify privacy. Capture sanitization and reproduction generation are Phase 2/4 work.

## Implemented Phase 2 architecture (supersedes capture proposals above)

The consent popup queries the selected tab and opens a background full extension capture page. That page obtains a same-origin Web Lock (one report owner), validates the supported surface, and injects locally bundled `content.js` into the top frame's ISOLATED world. It binds `tabs.connect` to the injection's exact `documentId`. Only its authenticated extension origin can send start/stop/discard on that port. The content entry runs rrweb with masking/blocking, sanitizes snapshots/mutations through an explicit allowlist, and streams bounded packets. The capture page validates packets again and owns the sole bounded recording buffer. There is **no service worker**, storage permission, all-sites permission, web-accessible resource or backend. A closing/reloading controller disconnects the port and stops recording. The start query is consumed once to prevent reload from restarting capture.

`packages/recorder` now contains reusable recording behavior, safe packet schemas, buffer and page diagnostics; it is private, not an SDK release. `packages/core` adds the capture sanitizer and v2 replay-event subset. Reports v1 and v2 remain parseable; v1 cannot contain replay payloads. New captures use v2 with supported sanitized rrweb snapshots, mutations, pointer/focus/scroll/resize/input events. An available replay capability means DOM evidence was captured, **not** that a viewer exists. Arbitrary custom/plugin/CSS/font/canvas/media/selection events are not retained. No custom DOM recording/replay engine was written.

The controller also injects `page.js` into MAIN and starts error/rejection listeners and a native PerformanceObserver. **Fetch/XHR are never wrapped or replaced.** Resource Timing exposes completed HTTP-failure metadata without changing application promises, responses, exceptions or cancellation. Request methods are unavailable (`OTHER`); opaque statuses, network errors, aborts/timeouts, worker requests and pending/unconsumed fetch responses may be missing. The demo now consumes its own JSON error response to finalize the timing entry; recorder code never reads it. Requests begun before observation are ignored. Page exceptions retain available numeric line/column only; rejection reasons are never read. A source/origin/session/schema/size/rate checked page message bridge carries only sanitized diagnostic packets. It never accepts privileged commands. A hostile page can still forge or suppress plausible diagnostics, so the page bridge is not an authentication boundary.

Full navigation/reload, source-tab closure, indicator removal/hiding or port failure ends capture with an explicit reason; already-received evidence stays in the open capture page. Closing/reloading that page or restarting the browser loses it. Same-document navigation is observed with Chromium's Navigation API, without patching history. The page indicator is excluded from rrweb and interaction capture. Stop/discard remove observers, listeners, timers and indicator; an idle isolated connection bootstrap remains until document navigation. There is no automatic restart.

Limits are enforced before acceptance: 300,000 ms, 10,000 combined evidence/timeline events, 5 MiB serialized report with final-metadata reserve; 1,000 errors/requests per channel; 512 KiB per DOM event; 5,000 nodes and 64 DOM levels per sanitizer traversal. Report parsing rejects nesting beyond 80 JSON levels before recursive schema evaluation. Unknown/malformed evidence fails closed. Text and identifiers are masked, URL origins remain visible, all paths/queries/fragments/userinfo are redacted, and external assets/styles are omitted. Details: [privacy](privacy.md), [Phase 2 evidence](verification-phase2.md).

Current API references: [document-scoped scripting](https://developer.chrome.com/docs/extensions/reference/api/scripting), [long-lived messaging and port lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/messaging), [Resource Timing status](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming/responseStatus), and [Chromium extension action testing protocol](https://github.com/ChromeDevTools/devtools-protocol/blob/master/json/browser_protocol.json). End-to-end tests exercise the actual extension bundles and grant temporary permission through the real action, not a test manifest with broader host permissions.

## Implemented Phase 3 investigation

The dashboard and full extension page share `LocalReports`, `ReportViewer` and `Replay`. Each owns one report in React memory. The capture controller transfers its stopped report and releases its recording buffer. Metadata is validated on save; unsaved edits disable export. Import validates a bounded local file before replacement confirmation. Abort signals invalidate late reads. Export validates again, serializes version 1/2 JSON and downloads an ID-based `.reprokit.json`. Removing a report destroys the viewer/replay; browser downloads remain outside app retention. There is no persistent report list, account, API, upload or backend.

Timeline/errors/requests render escaped text, with 50-row pagination and a timeline type filter. Context shows source, environment, capabilities and limitations without assuming web evidence. Replay and unsupported capabilities have explicit unavailable states. No steps or Playwright source are generated in this phase.

`@rrweb/replay` 2.2.0 runs as a bundled trusted IIFE inside a **naturally opaque data document**. The outer frame permits scripts/same-origin access but is not same-origin with its embedding app. The initial sandbox-origin-flag design (`sandbox="allow-scripts"` on a normal URL) was rejected because that flag propagates to the nested frame and prevents rrweb's supported direct DOM access. No unsafe rrweb rebuild was enabled to work around it. The final driver uses rrweb's supported script-disabled `allow-same-origin` child; its captured nodes cannot execute scripts. See [upstream sandbox guidance](https://rrweb.com/docs/sandbox), [canvas safety](https://rrweb.com/docs/recipes/canvas), and [data URL opaque origins](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/data).

Only trusted static document/code/style URLs enter the data bootstrap; report JSON crosses via source/session-checked postMessage and is validated again. Restrictive CSP plus the strict resource-free DOM subset prevent report-driven network/assets. The extension adds two public static renderer resources, `replay.js`/`replay.css`, with no new permissions or report access. Vite emits the standalone IIFE separately so extension replay needs neither inline JS nor eval. The dev plugin compiles these assets at server startup and serves them without Vite HTML/HMR injection; restart after driver changes. [Phase 3 verification](verification-phase3.md) records automated isolation probes and actual capture/export/import evidence.

## Phase 3 replay layout correction

New captures use report v3; v1 and unstyled v2 remain readable. v3 adds an optional canonical `style` attribute restricted by a shared property/value allowlist. The recorder uses rrweb's public `record.mirror` to find each retained live element and reads only selected resolved presentation values. It never copies stylesheets, selectors, custom properties, generated strings or resource URLs. Font family names become generic local families. The browser's resolved values preserve common grid/flex layouts, dimensions, spacing, borders and colours. See [getComputedStyle](https://developer.mozilla.org/en-US/docs/Web/API/Window/getComputedStyle) and [rrweb mirror](https://rrweb.com/glossary/mirror).

Snapshot/new nodes receive presentation attributes before streaming. Observed changes schedule a coalesced 100ms scan of at most 5,000 tracked elements; only changed presentation becomes an ordinary rrweb attribute mutation. Stop flushes pending presentation, and the controller drains validated final packets until acknowledgement/disconnect or a bounded 1s timeout. Arbitrary-page activity does not gain a privileged message path. rrweb seek uses a one-millisecond inclusive boundary so the final event is applied when seeking to End.

The same declaration rules sanitize capture packets and strictly validate imports; arbitrary CSS and resource-loading properties remain forbidden. Each node's presentation is bounded to 4,096 characters; existing DOM-event/report/time/count limits remain enforced. Styles count toward those limits and may end complex recordings earlier. The extension adds `style-src-attr 'unsafe-inline'` solely to let validated inline presentation render under the inherited CSP. Script policy, stylesheet-element restrictions, no-network CSP, opaque outer origin and script-disabled captured frame remain intact. Existing exports cannot recover CSS that was already discarded. [Verification and remaining fidelity limits](verification-replay-layout.md).

## Implemented Phase 4 reproduction

`packages/core/src/reproduction.ts` deterministically derives bounded steps and editable Playwright source from validated web actions. It does not use rrweb DOM events to guess selectors, setup or assertions. `packages/recorder/src/locators.ts` retains a unique short test ID, otherwise a unique supported control role without a name. Raw attributes/names stay outside replay. Clicks use the nearest interactive ancestor; input metadata records text/password/other, never values or checked state. The buffer revalidates locators, reserves 64 KiB for bounded steps/final metadata and derives suggestedSteps at stop.

New reports use v4; v1–v3 remain readable. Only v4 web reports with actions may declare Playwright-draft availability. The optional inputKind field belongs only to v4 input actions. Legacy web actions can still produce a UI draft with explicit gaps; the older report's recorded capability declaration remains historical. Reproduction is unavailable for non-web/empty evidence.

The shared Reproduction pane lazily creates one draft per report view, preserves edits while navigating, and exports exactly the edited `.spec.ts`. Source edits do not modify report JSON and never execute in either viewer. All data literals are JSON-quoted with HTML/line-separator escaping; captured strings never enter comments. Missing locators/routes, masked inputs, unsupported controls, truncation and missing assertions stop with TODO errors. There are no invented business assertions or implicit authentication fixtures, and no timing sleeps. See official [locators](https://playwright.dev/docs/locators), [fill API](https://playwright.dev/docs/api/class-locator#locator-fill) and [assertions](https://playwright.dev/docs/test-assertions).

Acceptance runs an actual extension-captured/exported test in a separate Playwright runner. Author-supplied assertions first confirm the observed unsaved state, then intentionally fail the demo's stated intended saved-state behavior. This separates a generated action sequence, unfinished guards and real application failure. [Phase 4 verification](verification-phase4.md). Phase 4 itself required no hosted service.

## Implemented Phase 5 hosted boundary

The dashboard optionally uses `@supabase/supabase-js@2.118.0` for PKCE email/password auth, confirmation/reset, session persistence/refresh, owner project/report queries and status updates. Local capture and report memory remain separate. A build-time public-key guard rejects accidental privileged browser keys. Signing out destroys hosted viewer state; a failed upload or refresh preserves the local report. Imports are local until an explicit reviewed upload. Concurrent viewers use unique React label IDs. The extension has no hosted tokens or upload capability in this phase.

`supabase/migrations/202611040001_hosted_reports.sql` defines owner-scoped projects/reports, composite project/owner integrity, column-only status updates, RLS and a private `recordings` bucket. Clients cannot insert/delete report rows, write counters, call service mutation RPCs, or directly sign/read/write/delete objects. A restrictive bucket policy also denies access through an unrelated permissive policy. Only the server's privileged client performs ingestion and object operations, after `auth.getUser` validates the bearer session. CORS restricts browser origins but grants no authentication. [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Storage access](https://supabase.com/docs/guides/storage/security/access-control).

The Edge Function streams at most 5 MiB, with bounded read/fetch timeouts and fatal UTF-8 validation, then parses through the exact shared core validator bundled by `npm run build:hosted`. Unknown fields/versions and hostile replay are rejected before storage reservation. Canonical JSON gets a SHA-256 hash. Server-generated object paths are owner/server-report UUIDs; clients never supply paths. Twenty attempts/hour/account are charged before body reading, with 25 projects and 100 reports/account. These caps bound per-account ingestion rather than promising global protection against unlimited malicious accounts; configure provider Auth abuse controls and monitor usage before wider hosting.

Upload reserves pending metadata under an advisory lock and a 15-minute lease, writes Storage, then completes only the current lease. Identical completed reports are idempotent; different content under the same project/source report ID conflicts. A failed write/completion retains pending work for retry. The lease exceeds the documented maximum Edge worker duration, reducing stale-worker races. Delete marks a leased row, calls Storage remove, then deletes metadata; it never deletes Storage metadata with SQL. Failed deletes stay queued. `claim_cleanup` uses row locks/skip-locked batches of 50, claims expired ready reports, pending work older than an hour and unfinished deletions. See [Storage schema warning](https://supabase.com/docs/guides/storage/schema/design) and [Edge limits](https://supabase.com/docs/guides/functions/limits).

Reads require current ownership, ready lifecycle and unexpired 30-day retention; the function mints a 60-second signed URL. Signed URLs are temporary bearer access and should not be shared/logged. Existing issued URLs can remain usable until expiry. Cleanup requires a separate server-only random secret, compared by digest, stored in function secrets and Vault. The owner-run Cron/pg_net schedule invokes it every 15 minutes. Outages/backlogs can delay physical deletion; failed leased work can retry. Job enqueue success is not an HTTP success guarantee. Provider backups have separate retention. [Official scheduled function pattern](https://supabase.com/docs/guides/functions/schedule-functions).

PGlite runs the actual migration/RLS in PostgreSQL; handler fault tests simulate provider adapters; routine hosted browser tests intercept synthetic transport. Separate live acceptance now verifies real Auth/API/Storage with two synthetic accounts, a real extension capture/export/import/upload/investigation flow, and scheduled expired-object/metadata deletion. Temporary owner/report-scoped triggers caused real completion/deletion RPC failures after Storage succeeded; the deployed function retained work and retries completed safely. All fixture triggers/functions/accounts/reports were removed and existing user projects preserved. The agent inspected the existing migration without rerunning it, installed the authorized function/secrets/Auth redirects and Vault/Cron schedule, and restored the normal 15-minute interval after a one-minute verification window. The owner confirmed real confirmation/reset email delivery and links. [Setup and runbook](hosted-setup.md), [Phase 5 evidence](verification-phase5.md).
